# Архитектура FunTime

## Сервисы

```text
Browser → HTTPS / Caddy → Gateway → gRPC Catalog
                                 → gRPC Room → gRPC GameRuntime
                                        ↓              ↓
                                   Rooms PostgreSQL  World PostgreSQL
```

Catalog хранит метаданные игр. Gateway предоставляет HTTP, устанавливает cookie, ограничивает тело и время запросов, проверяет Origin и скрывает внутренние ошибки. Room владеет кодом, участниками, ролями и привязкой к партии. World Domination владеет правилами, фазами, таймером, планами, переговорами и результатами.

У каждого сервиса отдельный Go-модуль, процесс и образ. Общий `packages/go` содержит только технические средства хранения и запуска. Room не импортирует правила конкретной игры: игровой сервис подключается через реестр клиентов `GameRuntime`, возвращает определение стран/ролей и фильтрованный JSON-снимок.

## FSD и запросы

Импорты направлены вниз: app → pages → widgets → features → entities → shared. Публичные API слайсов — index.ts; проверка — scripts/check-fsd.mjs.

- app: Redux store, Provider, подписки RTK, маршруты и глобальные стили.
- pages/home: каталог и его композиция.
- pages/room: композиция лобби, пульта, общего экрана и игрового интерфейса.
- widgets/world-summary: сводка, график, результаты и журнал.
- features/enter-room, world-orders, world-diplomacy: пользовательские действия.
- entities/game, room, world-domination: модели и API соответствующих сущностей.
- shared: baseApi, генерируемые транспортные типы, UI и семантические токены тем.

Все HTTP-запросы выполняет RTK Query. Каталог кешируется; комнаты опрашиваются каждые две секунды и обновляются после команд. После потери связи остаётся последний снимок с уведомлением, запросы продолжаются. WebSocket пока не используется. Таймер отображается локально с поправкой на serverTime, но переходами управляет сервер.

Общий план имеет version. Сервер отклоняет устаревшую запись кодом 409, UI предлагает загрузить план товарища, сохраняя черновик до явного действия. При смене фазы черновик сбрасывается: участвуют только сохранённые планы.

Темы находятся в shared/styles/themes.css. Игровые экраны используют эти же CSS variables; смена темы не затрагивает модель или сетевой слой.

## Состояние и доступ

Случайные токены сессий хранятся в браузере только в HttpOnly SameSite=Strict cookie, ограниченной путём комнаты; в БД хранится SHA-256 токена. В production cookie Secure. Код комнаты является приглашением и даёт доступ к публичной проекции, но не к чужой сессии.

Проекции строятся явно:
- общий экран: состав участников, фаза, экология, развитие городов и таблица очков;
- команда: дополнительно собственные деньги, щиты, программа, бомбы, план и относящиеся к ней переговоры;
- ведущий: полные игровые данные;
- после финала: источники атак становятся публичными; донор остаётся скрыт от получателя.

Публичный endpoint игнорирует даже cookie ведущего. Проверка прав выполняется в сервисе-владельце, а не через скрытие кнопок.

Каждая мутация сначала сохраняется, затем становится видимой. Ошибка записи не меняет опубликованное состояние. PostgreSQL хранит атомарные JSONB-документы в собственной БД сервиса. Локальный режим использует временный файл, fsync и замену файла в .cache/data. Это режим для одного процесса, без обещания распределённых транзакций.

Запуск: lobby → starting (сохранено) → идемпотентный Create(matchId=code) → playing. Повтор после сетевой ошибки продолжает запуск без обнуления партии.

Игровые команды имеют requestId; хранятся последние 4096 ключей participant+requestId. Version плана и expectedPhase дополнительно защищают от устаревших команд. Идентификаторы завершённых запросов и сами планы переживают перезапуск.

Сервер проверяет таймер раз в секунду. После простоя истёкшая фаза переключается один раз, следующая получает полную длительность: игра не пролетает все раунды без участников. Пауза сохраняется. В текущей версии все комнаты одного сервиса сериализуются mutex; это ограничивает пропускную способность.

## Добавление игры

1. Создать собственный сервис, реализующий contracts/proto/runtime/v1.
2. Добавить его клиент в реестр Room и метаданные в Catalog.
3. Создать FSD-слайсы игровой модели, действий и представления; подключить композицию в странице комнаты.
4. Добавить Dockerfile, dev-запуск, Compose и тесты.

JSON внутри GameRuntime — версионированный игровой контракт, а не сериализация внутреннего состояния. Его публичная схема описывается в OpenAPI. При несовместимых изменениях нужен новый контракт/версия игры; миграции уже сохранённых партий пока не реализованы.

## Эксплуатация

Нативный dev: Gateway 8080; Catalog gRPC 9001/health 9002; Room 9003/9004; World Domination 9005/9006; Vite 5173.

Compose: один хост, Caddy, Nginx, четыре Go-сервиса, два PostgreSQL. Только Caddy публикует порты. Go-контейнеры работают без root с read-only filesystem; состояние находится в БД. Внутренний gRPC без TLS ограничен закрытой сетью хоста.

Room и игровой сервис должны иметь единственного владельца состояния. Перед несколькими репликами нужны распределённая блокировка/назначение владельца и контроль ревизии в БД. Текущий Compose не обеспечивает высокую доступность, автоматический backup или бесшовный deploy.

CI проверяет генерацию контрактов, TypeScript/ESLint/FSD, Go, браузерные сценарии и сборку контейнеров.
