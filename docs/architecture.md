# Архитектура FunTime

## Реализованный этап

```text
React → HTTP /api/v1/games → Gateway → gRPC → Catalog Service
```

Gateway и Catalog Service — независимые Go-модули и процессы. Их связывает только сгенерированный контракт. Catalog Service возвращает каталог; Gateway преобразует Protobuf в публичный HTTP DTO, ограничивает время запроса и скрывает внутренние ошибки. Frontend проверяет структуру полученного JSON во время выполнения.

Каталог пока задаётся в `services/catalog/internal/catalog/service.go`: одна игра со статусом `coming_soon`. Постоянное хранилище для этого этапа не требуется. Количество карточек, поиск и фильтр работают по ответу API. Сетевую ошибку не подменяем локальным каталогом.

## Frontend / FSD

Зависимости направлены вниз: `app → pages → widgets → features → entities → shared`.

- `app`: запуск, маршруты, глобальные стили.
- `pages/home`: композиция стартового экрана, состояние загрузки, поиск и фильтр, уникальные иллюстрации, информационные окна. Эти функции пока не переиспользуются, поэтому остаются в странице.
- `pages/not-found`: обработка неизвестных маршрутов.
- `widgets/app-header`: шапка и навигация.
- `features/switch-theme`: переключение темы пользователем.
- `entities/game`: тип игры, API каталога, валидация, общая карточка со слотом иллюстрации и обработчиком действия.
- `shared`: UI, HTTP-клиент, транспортные типы, техническая логика темы и CSS-токены.

Слайсы доступны через `index.ts`. Импорты между соседними слайсами запрещены. `scripts/check-fsd.mjs` проверяет статические импорты, реэкспорты и строковые динамические импорты TypeScript. Для `app` и `shared` действуют стандартные исключения FSD. Это проверка импортов исходников, а не гарантия отсутствия любых возможных архитектурных нарушений.

Светлая и тёмная темы описаны в `shared/styles/themes.css`. UI использует семантические CSS variables. Декоративные иллюстрации сохраняют собственные художественные палитры; их можно заменить независимо от карточек и API. Настройка темы сохраняется локально, синхронизируется между вкладками и применяется до загрузки React. При недоступном localStorage переключение продолжает работать в текущей вкладке. Шрифты поставляются вместе с приложением.

## Добавление игр

На этапе каталога добавьте метаданные в Catalog Service. Неизвестные иллюстрации отображаются с общей иконкой.

После реализации партий уникальные экраны будут находиться в `pages/<game>`. Переиспользуемые модели и действия можно выделять в соответствующие слайсы `entities` и `features`. Реестр маршрутов подключается в `app`; каталог и лобби не импортируют игровые страницы.

Каждая полноценная игра получает собственный Go-сервис. Планируемый общий контракт: определение версии и возможностей, проверка настроек, создание партии, обработка команды, получение доступного участнику представления, статус и результат. Точные сообщения определим при реализации комнат и правил.

## Следующие сервисы

- **Room Service**: гостевые сессии, коды, участники, ведущий, лобби, готовность, запуск и привязка партии к игровому сервису.
- **World Domination Service**: состояние партии, правила, таймеры, действия, скрытая информация, очки и результаты.

Room Service владеет комнатой; игровой сервис — партией. У каждого собственная база PostgreSQL и учётная запись, без доступа к чужим таблицам. Gateway проксирует команды и потоки; бизнес-права проверяет сервис-владелец.

Запуск партии станет восстанавливаемой операцией `starting → in_progress` с устойчивым `matchId` и повторяемым `CreateMatch`. Таймаут не трактуется как гарантированный отказ создания. Команды имеют `requestId`; обновления — ревизию. Переподключение получает снимок состояния для конкретного участника. Правила очков не выполняются на клиенте.

Для каждого экземпляра партии нужен единственный владелец. Перед горизонтальным масштабированием реализуем назначение владельца и защиту от одновременного изменения состояния двумя экземплярами. При несовместимых обновлениях старые партии заканчиваются на прежней версии, новые запускаются на новой.

## Deploy

Первый вариант: один Linux-сервер, Compose, Caddy и три образа приложения. Разделение контейнеров уже соответствует микросервисным границам. Production использует опубликованные образы по digest; локальный Compose собирает их из исходников. Контейнеры Go работают без root, с файловой системой только для чтения и завершением по SIGTERM.

Внешний HTTPS заканчивается в Caddy. Внутренний gRPC использует незашифрованный канал только внутри закрытой сети одного хоста. При переносе сервисов на разные хосты требуется защищённый транспорт и аутентификация сервисов.

Compose на одном хосте не обеспечивает высокую доступность или деплой без прерывания соединений. Публикация образов, секреты реального окружения, автоматический деплой и откат появятся после выбора инфраструктуры. База, резервные копии и WebSocket на текущем этапе отсутствуют, поскольку комнаты ещё не реализованы.
